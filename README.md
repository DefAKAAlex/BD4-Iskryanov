## Задание 1. Резервное копирование*
*Кейс*
*Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования.*
*Необходимо описать, какие варианты резервного копирования подходят в случаях:*

### 1.1. Восстановление данных в полном объёме за предыдущий день
Для этого случая оптимально использовать комбинированную стратегию: Полное резервное копирование + Журналы транзакций.

Здесь можно выбрать два вариант:
* Полный бэкап + Дифференциальный бэкап
* Полный бэкап + Инкрементный бэкап

В первом случае схема следующая:
+ Полный бэкап (в воскресенье в 00:00)
+ Дифференциальный бэкап (ежедневно в 00:00) — сохраняет изменения с момента последнего полного бэкапа
+ Для восстановления за предыдущий день: Полный бэкап + Дифференциальный бэкап за нужный день

Во-втором:
+ Полный бэкап (каждое воскресенье в 00:00)
+ Инкрементные бэкапы (ежедневно в 00:00)
+ Для восстановления: Полный бэкап + Все инкрементные бэкапы по порядку

В первом случае получается более надёжный вариант, потому как управление восстановлением проще и надёжнее. Из минусов - большой размер бэкапов, но, финансовой компании этот вариант подойдёт больше.

### 1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.

Для этого случая лучше будет использовать *Point-in-Time Recovery*.\
Полный бэкап раз в неделю, как и в вопросе 1.1.

Метод PITR позволяет восстановливать базу с точностью до секунды.

### 1.3* Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных

Да, такой кейс возможен.\
Используя несколько slave-ов в репликации к Master.\
Automatic Failover позволяет автоматически поднимает один из slave-ов до Master и переключается на него, в случае если Master падает.

## Задание 2. PostgreSQL

### 2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).

Для резервного копирования и восстановления в PostgreSQL используются утилиты **pg_dump** и **pg_restore**/**psql**.
Принцип их работы: **pg_dump** создает "слепок" базы данных на момент запуска, не блокируя её работу.

* для резервирования данных:
в простой sql-файл

>pg_dump -U postgres -h localhost -d mydb > mydb_backup.sql

в кастомный формат

>pg_dump -U postgres -h localhost -d mydb -Fc -f mydb_backup.dump

<br>

* для восстановления:
из sql-файла

>psql -U postgres -h localhost -d newdb -f mydb_backup.sql

при этом *newbd* нужно создать заранее

из кастомного дампа

в существующую базу

>pg_restore -U postgres -h localhost -d newdb mydb_backup.dump

с созданием базы

>pg_restore -U postgres -h localhost -C -d postgres mydb_backup.dump

здесь ключ **-С** создаёт новую базу


## Задание 3. MySQL

### 3.1. С помощью официальной документации приведите пример команды инкрементного резервного копирования базы данных MySQL.

Инкрементное копирование в MySQL реализуется через резервное копирование бинарных логов.

Процесс состоит из двух этапов: создается полная копия, затем — инкрементные на основе бинарных логов.

* создание полного бэкапа
>mysqldump -u root -p --all-databases --single-transaction --flush-logs --master-data=2 > full_backup.sql

здесь *--flush-logs* заверщает текущий файл бинарного лога и начинает новый.

* создание инкрементного бэкапа

После полного бэкапа все новые изменения будут записываться в новый бинарный лог. Сам инкрементный бэкап — это копия этого лога в безопасное место .


>mysqlbinlog /var/log/mysql/mysql-bin.000001 > incremental_backup_1.sql

Для регулярного бэкапа, нужно копировать файлы бинарных логов по расписанию.

### 3.1. В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием?
* Главным плюсом является отсутствие нагрузки на основной сервер, так как создание бэкапа обычно происходи на реплике.
* "Горячее" резервное копирование. Можно остановить процесс репликации и безопасно сделать снимок и запустить репликацию снова.
* Реплику можно использовать для аналитики и тестирования, что гарантирует безопасность основной системы
